# 09 — Web3 and Blockchain

Authority over: the smart contract, Merkle batching, anchoring, and chain reads.

---

## 1. Why a chain at all

Delta needs one property: **a third party must be able to tell that an
approved record has not changed since approval, without trusting Delta's
database or Delta's word.**

A signed log or a timestamping authority would also work; the chain is chosen
because it is publicly readable with no account, no key and no permission.
This trade-off is recorded in `ADR-0002`.

What goes on chain is a **Merkle root** — one 32-byte value per batch.
Never a photograph, never personal data, never coordinates, never a manifest.

## 2. Non-goals

No tokens. No NFTs. No wallet connection. No user ever signs a transaction.
No gas is ever requested from a user. No mainnet. One chain only:
**Base Sepolia, chain id 84532.**

The word "blockchain" appears in exactly one section of the landing page and
in the chain panel of the proof dossier. Nowhere else.

## 3. The contract

`contracts/src/ImpactAnchorRegistry.sol`

- Solidity `>=0.8.24`, OpenZeppelin v5
- Inherits `Ownable2Step` — two-step ownership transfer, no single-call
  handover to a wrong address
- Built and tested with Foundry. **Hardhat is forbidden.**

### Surface

```solidity
struct BatchAnchor {
    bytes32 merkleRoot;
    uint64  anchoredAt;
    uint32  leafCount;
}

mapping(uint256 batchId => BatchAnchor) public anchors;

event BatchAnchored(uint256 indexed batchId, bytes32 merkleRoot, uint32 leafCount, uint64 anchoredAt);
event AnchorerSet(address indexed anchorer, bool authorized);

function setAnchorer(address anchorer, bool authorized) external onlyOwner;
function anchorBatch(uint256 batchId, bytes32 merkleRoot, uint32 leafCount) external onlyAnchorer;
function getAnchor(uint256 batchId) external view returns (BatchAnchor memory);
function verify(uint256 batchId, bytes32[] calldata proof, bytes32 leaf) external view returns (bool);
```

### Required behaviour

- Only an authorised anchorer may anchor. Owner manages the anchorer set.
- A `batchId` can be anchored **once**. A second attempt reverts.
- Zero root and zero address revert.
- `leafCount` of zero reverts.
- `verify` uses OpenZeppelin `MerkleProof.verify` and is a pure view — anyone
  can call it over `eth_call` with no key.

### The contract does not

Store images, run AI, calculate impact, hold funds, mint anything, or make
any decision. It stores roots and answers questions about them.

### Foundry tests — `contracts/test/ImpactAnchorRegistry.t.sol`

| Test | Asserts |
|---|---|
| unauthorised anchor | reverts |
| duplicate `batchId` | reverts |
| zero root / zero `leafCount` | reverts |
| two-step ownership | pending owner must accept; direct transfer does not take effect |
| valid proof | `verify` returns true |
| wrong leaf, wrong batch, tampered proof | `verify` returns false |
| fuzz over `batchId` and root | no collisions, no overwrite |
| event emission | correct arguments |

`forge test -vvv` must be green before deployment. Deploy with
`contracts/script/Deploy.s.sol`, then verify the source on BaseScan — an
unverified contract is unreadable to the public and defeats the purpose.

## 4. Merkle batching

```ts
StandardMerkleTree.of(leaves, ["bytes32", "bytes32", "uint256"])
// leaf = [submissionIdBytes32, manifestHashBytes32, approvedTimestamp]
```

- Leaves sorted ascending by `submissionId` — deterministic, reproducible
- `approvedTimestamp` is Unix seconds UTC
- The tree, root, each leaf's index and each leaf's proof are persisted in
  `anchor_batch` and `anchor_leaf` before the transaction is sent
- Documented in `ADR-0005`

Batching rather than one transaction per submission: one daily transaction
anchors any number of approvals. This is why the free tier is sufficient at
scale, and it is a legitimate engineering answer to a real cost constraint —
say so in the README.

## 5. Anchoring flow

```
1. Select APPROVED submissions with manifest_hash set and no anchor_leaf
2. Build the canonical manifest for each (src/lib/crypto — frozen)
3. Build the Merkle tree
4. Write anchor_batch (PENDING) + anchor_leaf rows, with proofs
5. Send anchorBatch() via viem with the server signer
6. Mark SUBMITTED, store tx_hash
7. Poll for the receipt
8. On confirmation: mark CONFIRMED, store block_number, move submissions to
   ANCHORED, append an audit_event per organisation
9. On revert: mark FAILED with the reason. Submissions stay APPROVED and are
   picked up by the next batch
```

Triggered by a daily cron at `/api/internal/anchor/daily` (guarded by
`CRON_SECRET`) and by the admin "Anchor now" button.

The database write happens **before** the transaction is sent. If the process
dies mid-flight, a `SUBMITTED` batch with a `tx_hash` is recoverable by
polling. A batch that only exists on chain and not in the database is not.

## 6. Key handling

- `ANCHOR_PRIVATE_KEY` lives in server environment only. It is never
  `NEXT_PUBLIC_`, never in a client component, never logged, never in an
  error message, never written to the database.
- The signer is constructed inside `anchor.service.ts` and used nowhere else.
- A grep for `ANCHOR_PRIVATE_KEY` must return exactly one source file. Make
  that an assertion in `check-forbidden-deps.mjs`.
- The account holds testnet funds only. State in the README that compromise
  of this key allows an attacker to anchor junk batches but cannot alter or
  delete existing anchors — `Ownable2Step` plus single-anchor-per-batch
  bounds the damage.

## 7. Client-side verification

The proof page verifies in the visitor's browser. This is the whole point —
a server-asserted "verified ✓" proves nothing.

```
1. Fetch the canonical manifest from /api/v1/submissions/[id]/proof
2. Recompute manifestHash = SHA256(canonicalize(manifest)) with crypto.subtle
3. Rebuild the leaf
4. eth_call verify(batchId, proof, leaf) against Base Sepolia via viem
5. Render MATCH / MISMATCH / PENDING / UNAVAILABLE
```

A public RPC endpoint is used for reads. No key is required for `eth_call`,
so no secret reaches the browser.

Show the work: the page displays the manifest JSON it hashed, the hash it
computed, the leaf, the proof path and the root it checked against. A visitor
who does not trust the page can redo every step with `cast` from a terminal.

### Drop the original photo

`crypto.subtle.digest("SHA-256", fileBytes)` in the browser, compared to
the `sha256` of each entry in the manifest's `files` array. The file never leaves the
device — state this on the page, next to the dropzone, not in a footnote.

## 8. Failure states

| Condition | Shown |
|---|---|
| RPC unreachable | `UNAVAILABLE`, neutral grey |
| Batch not yet confirmed | `PENDING`, amber |
| Hash differs from anchored leaf | `MISMATCH`, red |
| Proof valid | `MATCH`, chain violet |

`UNAVAILABLE` must never render as `MISMATCH`. A network problem shown as
evidence of tampering is the most damaging bug this page can have.

## 9. Amendments

A record amended after anchoring gets `manifest_version + 1` and is anchored
in a later batch as a new leaf. The previous version's anchor remains valid
and remains visible. The proof page shows every version with its own
verification result and the reason for the amendment.

Never re-anchor a version. Never overwrite a leaf. The unique constraint on
`(submission_id, manifest_version)` enforces this at the database level.
