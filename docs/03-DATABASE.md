# 03 — Database

Authority over: schema, extensions, indexes, immutability enforcement.

## 1. Engine and driver

| | |
|---|---|
| Engine | PostgreSQL 17 with PostGIS and pgvector |
| Local | `docker/db.Dockerfile` — `postgis/postgis:17-3.5` + `postgresql-17-pgvector` |
| Hosted | Neon free tier |
| ORM | `drizzle-orm` stable `0.x` — use `relations()`, never `defineRelations()` |
| Driver | **`postgres` (postgres.js) over TCP** |

### 1.1 Driver rule — non-negotiable

**Do not use `@neondatabase/serverless` with `drizzle-orm/neon-http`.**

The HTTP driver throws `No transactions support in neon-http driver`.
Transactions require a stateful connection, which HTTP does not provide.
Delta's entire integrity model depends on transactions:

- `pg_advisory_xact_lock` for the per-organisation audit chain
- `SELECT … FOR UPDATE SKIP LOCKED` for the job queue
- Atomic state transition + finding writes + audit append

Use `postgres.js`:

```ts
// src/server/db/client.ts
import "server-only";
import postgres from "postgres";
import { drizzle } from "drizzle-orm/postgres-js";
import * as schema from "./schema";

const sql = postgres(process.env.DATABASE_URL!, { prepare: false, max: 5 });
export const db = drizzle(sql, { schema });
```

- Runtime uses the **pooled** `DATABASE_URL` with `prepare: false`
- Migrations use **`DATABASE_URL_UNPOOLED`**
- Keep `max` small; the hosted free tier has limited compute

## 3. Custom Drizzle column types

### `geographyPolygon` / `geographyPoint`
`geography(Polygon, 4326)` and `geography(Point, 4326)`.

Use **`geography`**, not `geometry`. Geography gives metre-accurate
`ST_DWithin` and `ST_Distance` on a sphere without reprojection, which is
what a "within 500 m of the boundary" check actually needs.

- `toDriver`: GeoJSON → `ST_GeomFromGeoJSON(…)::geography`
- `fromDriver`: parse EWKB hex → GeoJSON. Guarantee `[longitude, latitude]` order.

### `bit64`
`bit(64)`, stored as a 64-character `'0'|'1'` string.

**`forensic_finding`** — one row per signal, the product's core artefact.

| Column | Type |
|---|---|
| `id` | uuid PK |
| `submission_id` | uuid FK |
| `evidence_file_id` | uuid FK → evidence_file, nullable — the specific file the finding concerns |
| `kind` | enum — see `docs/10-FORENSICS.md` |
| `severity` | enum `INFO`,`LOW`,`MEDIUM`,`HIGH` |
| `reason` | text — human-readable, shown verbatim in the Lab |
| `evidence` | jsonb — the literal inputs (distances, hashes, thresholds) |
| `rule_version` | text — e.g. `forensics.v1` |
| `created_at` | timestamptz |

`evidence` is what powers the "why was this flagged?" drill-down. It must
contain enough to recompute the verdict by hand.

**`risk_score`, `risk_band` and `scoring_version` on `evidence_submission` are
a cache of a pure function of the findings**, stored so a Lab queue of
thousands of rows can be sorted without a join. Four conditions:

1. They are **only ever written by the pure function** in
   `src/lib/scoring/`. Never by hand, never by the AI, never by an admin.
2. `scoring_version` is stored with them, so a weights change does not
   silently rewrite history. Old submissions keep their original version.
3. They are **never rendered without the findings beside them.**
4. They never gate a transition.

See `docs/10-FORENSICS.md` §6.

## 5. Append-only enforcement

Convention is not enforcement. Both of these, in a migration:

```sql
REVOKE UPDATE, DELETE ON review_decision, audit_event, anchor_leaf FROM PUBLIC;
REVOKE UPDATE, DELETE ON review_decision, audit_event, anchor_leaf FROM app_user;

CREATE OR REPLACE FUNCTION delta_block_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'append-only table: % is immutable', TG_TABLE_NAME;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_event_immutable
  BEFORE UPDATE OR DELETE ON audit_event
  FOR EACH ROW EXECUTE FUNCTION delta_block_mutation();
-- repeat for review_decision, anchor_leaf
```

An integration test must assert that a direct `UPDATE` on `audit_event`
raises.

## 7. Migration rules

- Every schema change goes through `drizzle-kit generate`. Never edit the
  database by hand, in any environment.
- Extensions, triggers, grants and HNSW indexes go in hand-written SQL
  migrations committed alongside the generated ones.
- Migrations are forward-only. No down migrations.
- Never `drizzle-kit push` against the hosted database.
- Review the generated SQL before applying. A generated `DROP COLUMN` on a
  hash or audit column is a stop-and-ask.

### 7.1 Geography typmod drift guard

drizzle-kit double-quotes any custom type it does not recognise, and
`"geography(Point, 4326)"` is not a valid identifier. So the schema declares
the custom types with a bare `geography` data type, and `drizzle-kit generate`
emits bare `geography` columns. `drizzle/0002_geography_typmod.sql` applies the
real typmod:

| Column | Type after `0002` |
|---|---|
| `impact_project.fuzzed_centroid` | `geography(Point,4326)` |
| `project_private_location.boundary` | `geography(Polygon,4326)` |
| `evidence_file.gps` | `geography(Point,4326)` |

Any future `drizzle-kit generate` that touches one of these columns may emit an
`ALTER COLUMN ... TYPE geography` that silently reverts the typmod. Read every
generated migration for that statement before applying it.

The guard is `scripts/check-geography-typmod.mjs` (`pnpm db:check-typmod`). It
reads PostGIS's `geography_columns` view (`information_schema` does not carry
typmod) and fails if any of the three columns has lost its geometry type or
SRID. Run it after every migration, against any database.
